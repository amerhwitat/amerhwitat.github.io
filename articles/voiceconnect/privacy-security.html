VoiceConnect privacy, security and deployment boundaries

VoiceConnect processes live audio/video, chat, profile data and signaling metadata. Operators should understand what remains local, what is shared with room participants, and what must be secured in a deployment.

Device permissions

Camera, microphone and screen capture should be requested only when the user invokes the relevant feature. The operating system or browser mediates access. Users can deny permission and should stop capture when sharing is no longer intended.

Profile and participant information

Nicknames and avatars are kept in the local profile and shared with room peers when the participant joins. The optional peer registry can store the signaling server's observed remote address and profile metadata only when the applicable opt-in is enabled. Behind a reverse proxy, forwarded headers must not be trusted unless the proxy overwrites untrusted values.

IP addresses and profile metadata are sensitive. Keep registries private, restrict filesystem access, define retention/deletion rules, and do not publish raw peer records.

Signaling, media and encryption

WebRTC media and data channels use WebRTC transport security, but public signaling still needs TLS/WSS. The optional application-level chat encryption feature is experimental and has not been independently audited; it must not be marketed as certified end-to-end encryption.

Room names alone do not authenticate users. Where invitation-token mode is enabled, protect signing secrets and admin credentials in deployment secret storage. Never embed them in the client bundle or commit them to source control.

TURN and operations

STUN assists with candidate discovery; TURN relays traffic when direct connectivity fails. A healthy HTTP endpoint or a configured TURN URL does not prove that media relay works. Validate real allocations and ICE relay candidates from external networks. The current repository deployment template documents TURN UDP/TCP on port 3478; it does not claim a TURN/TLS listener on port 443.

Before public deployment

  • Use HTTPS/WSS, strict origin allowlists and authenticated room access.
  • Apply per-user/per-room rate limits and abuse controls.
  • Protect TURN secrets, firewall rules, monitoring and logs.
  • Restrict and expire opt-in peer registry data.
  • Review Electron IPC, extension permissions, signaling authorization, file-transfer limits and cryptographic design.
  • Complete two-physical-device acceptance across distinct networks.
  • Obtain independent security review against the exact release commit.
  • Sign Windows binaries and sign/notarize macOS packages with valid credentials.

What CI can prove

CI can build packages, run automated tests, scan source and dependencies, produce an SBOM, and validate deployment configuration. It cannot establish real-world device behavior, TURN relay across arbitrary networks, production DNS/TLS, an independent penetration test, or a trusted publisher identity unless those specific gates are completed.
